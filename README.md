# HEC Pyrochlore Oxide Property Predictor

Machine-learning pipeline for predicting **lattice parameter**, **thermal conductivity**,
and **Vickers hardness** of high-entropy pyrochlore oxides (A₂B₂O₇) from composition alone.

> **Note on this README:** the sections below were reconstructed by reading the actual
> code (`src/`, `models/`) rather than relying on module docstrings, several of which are
> out of date. Where the code and its own comments disagree, the code's behavior is what's
> documented here, and the discrepancy is flagged in [Known Inconsistencies](#known-inconsistencies--stale-docs).

```
│   │   └── train_model.py     ← training, CV, feature importance, plots (shared by all models)

│
└── models/                    ← EXECUTABLE SCRIPTS (run these) + their generated output folders
    ├── predict_lattice.py        Predict lattice parameter interactively / via CLI
    ├── predict_rom_latt.py       Currently a byte-for-byte duplicate of predict_lattice.py (see Known Inconsistencies)
    ├── predict_thermal.py        Predict thermal conductivity (currently broken — see Known Inconsistencies)
    ├── validate_lattice.py       Full CV + feature-importance report for the lattice model
    ├── validate_rom_latt.py      Same, for the Rule-of-Mixtures-enriched lattice model
    ├── validate_rom_therm_cond.py  Same, for the ROM-enriched thermal-conductivity model
    ├── validate_rom_vickers.py     Same, for the ROM-enriched Vickers-hardness model
    ├── data_validation.py        Shared plotting helpers (target distribution, correlation
    │                              heatmap, residuals) called by the validate_*.py scripts
    ├── fill_pristine_data.py     ML gap-filling for data/processed/pristine_pyrochlore.csv
    │
    ├── lattice_param/            ← created by predict_lattice.py / validate_lattice.py
    ├── pristine_fill/            ← created by fill_pristine_data.py
    └── lattice_param_rom/, thermal_cond/, vick_hard/  ← created by the corresponding
                                     validate_rom_*.py script on first run
```

## Data

The project keeps two data tiers, `data/raw/` and `data/processed/`, but **the split is
not a strict "external input vs. pipeline output" split** — a few files in `data/raw/`
are themselves generated by scripts (see the "Origin" column below). The practical rule
that *is* consistently true:

- **`data/processed/`** — every file is deterministically rebuilt from `data/raw/` by
  `src/data/*.py` / `src/features/*.py` functions. Delete anything here and it will be
  regenerated the next time a `get_*_dataset()` call or a `models/*.py` script needs it.
- **`data/raw/`** — nothing here is *automatically* overwritten by the model-training
  pipeline (`load_data.py`, `make_combined_dataset.py`, `rule_of_mixture_cal.py`). But a
  few files are the saved output of a separate, manually-run **preprocessing** script
  (an AFLOW-merge script, a pymatgen-element-table dump, a JSON→CSV converter) — they're
  "raw" in the sense that the ML pipeline treats them as fixed inputs, not in the sense
  that no code ever wrote them.

imports a `get_thermal_dataset()` function that isn't defined anywhere in `load_data.py`
(only referenced, commented out, in that file's own `__main__` block). The thermal model
is only actually trainable today via the ROM path (`get_therm_cond_rom_dataset` →
`rom_hec_therm_cond.csv`). See [Known Inconsistencies](#known-inconsistencies--stale-docs).

### Does `data/processed/` contain all the data from `data/raw/`?

**No.** Three raw files are not reflected in any processed file at all, and several more
are only *partially* folded in depending on which processed file you look at:

- **Not processed by anything:**
  - `notebookLM_dataset.csv` — loader call is commented out in every builder.
  - `Jordan_pyrochlore_data.csv` — superseded by `Jordan_smaller.csv`, never read.
  - `check_df.csv` — an orphaned output, not a pipeline input at all.
- **Not directly processed, but used to build a file that *does* feed the pipeline:**
  `aflow_pyrochlore_data.csv`, `aflow_pyrochlore_data_extra.csv`,
  `aflow_pyrochlore_data_thermal.csv`, and `aflow_pyrochlore_data_coord.csv` are only
  consumed by `src/utils/combine_aflow.py`, which merges them into
  `aflow_pyrochlore_data_comb.csv` — that merged file is what actually reaches
  `pristine_pyrochlore.csv`.
- **Only partially reflected — depends on which processed file:**
  - `parent_components.csv` reaches `combined_pyrochlore.csv` but not `hec_pyrochlore.csv`
    or `pristine_pyrochlore.csv`.
  - `aflow_pyrochlore_data_comb.csv` and `mp_pyrochlore_query.csv` reach
    `pristine_pyrochlore.csv` but not `combined_pyrochlore.csv` or `hec_pyrochlore.csv`.
  - `Sample_Properties_Safin_Feb_2026.csv` reaches `combined_pyrochlore.csv` and
    `hec_pyrochlore.csv` but not `pristine_pyrochlore.csv`.
  - So no single processed file is a superset of all raw data — each is a
    *purpose-built subset*, and which raw sources go into which subset is controlled by
    the (sometimes commented-out) loader list at the top of each `build_*_dataset()`
    function in `src/data/make_combined_dataset.py`.

If you add a new raw file expecting it to "just show up" in `data/processed/`, it won't —
you also need to register a loader call in the relevant `build_*_dataset()` function (see
[Adding New Data](#adding-new-data)).

## Known Inconsistencies / Stale Docs

These were found while tracing the actual code paths; flagging them here so they don't
get re-documented as working features:

1. **`predict_thermal.py` is currently broken.** It does `from src.data.load_data import
   get_thermal_dataset, ...`, but `get_thermal_dataset` is not defined in `load_data.py`
   (only referenced, commented out, in that file's own `if __name__ == '__main__':`
   block). The only working thermal-conductivity path today is the ROM one
   (`validate_rom_therm_cond.py` / `get_therm_cond_rom_dataset`).
2. **`predict_rom_latt.py` is a byte-for-byte duplicate of `predict_lattice.py`** —
   despite the "rom" name, it imports `get_lattice_dataset` (the non-ROM function) and
   writes to the same `models/lattice_param/` directory. It does not currently exercise
   the Rule-of-Mixtures path.
3. **`validate_thermal.py` does not exist** — the original README referenced it, but the
   thermal-conductivity validation script is `validate_rom_therm_cond.py`.
4. **`make_combined_dataset.py`'s own module docstring is stale**: it says it combines
   "all four raw data sources," listing `notebookLM_dataset.csv` as #2, but the actual
   `load_nlm` call is commented out in all three `build_*_dataset()` functions.
5. **`data/raw/aflow_pyrochlore_data_comb.csv` is itself a build artifact**, written by
   `src/utils/combine_aflow.py` into `data/raw/` rather than `data/processed/`. If you
   need to refresh it, re-run that script rather than editing the CSV by hand.

## Quick Start

Run all scripts from the **project root** (`HECPyrochlore/`).

### Predict Lattice Parameter

**Interactive mode** (prompts for A-site and B-site elements):
```bash
python models/predict_lattice.py
```

**CLI mode** (single prediction):
```bash
python models/predict_lattice.py --a "Pr,Sm,Gd,Ho,Lu" --b "Ti"
python models/predict_lattice.py --a "La,Gd,Lu" --b "Ti,Zr"
```

**Force re-train** before predicting:
```bash
python models/predict_lattice.py --train --a "Sm,Eu,Gd,Tb,Dy" --b "Ti"
```

### Predict Thermal Conductivity

Not currently runnable — see [Known Inconsistencies](#known-inconsistencies--stale-docs) #1.
To train/validate a thermal-conductivity model today, use the ROM validation script below.

### Validate Models (Full Report + Plots)

```bash
python models/validate_lattice.py              # compositional-features-only lattice model
python models/validate_rom_latt.py              # Rule-of-Mixtures-enriched lattice model
python models/validate_rom_therm_cond.py        # Rule-of-Mixtures-enriched thermal-conductivity model
python models/validate_rom_vickers.py           # Rule-of-Mixtures-enriched Vickers-hardness model

# Custom number of CV folds:
python models/validate_lattice.py --splits 10
```

Each validation script prints:
- Cross-validation R², RMSE, MAE for all 4 candidate models (GradientBoosting, RandomForest, ExtraTrees, Ridge)
- Hold-out test-set metrics for the best model
- Top-15 features ranked by permutation importance and tree MDI
- Feature-group analysis (A-site vs. B-site vs. cross-site)
- Saves plots + a full text report to `models/<task>/` (see [Script Outputs](#script-outputs))

### Gap-fill the pristine lookup table

```bash
python models/fill_pristine_data.py
```

## Supported Elements

**A-site** (8-coordination, rare-earth cations):
`La Ce Pr Nd Sm Eu Gd Tb Dy Ho Er Tm Yb Lu Y`

**B-site** (6-coordination, transition metals):
`Ti Zr Hf Sn Ir Ce Nb`

Compositions are assumed **equiatomic** unless otherwise noted (non-equiatomic ICSD
entries carry exact mole fractions in `a_stoich_json` / `b_stoich_json`; see
[Data](#data) above).

## Feature Engineering

All features are derived purely from elemental properties — no DFT required.

| Feature Group | Examples | Physical Meaning |
|---|---|---|
| A-site | `a_site_entropy`, `a_site_mean_radius`, `a_site_delta` | Cation size disorder, configurational entropy |
| B-site | `b_site_entropy`, `b_site_mean_radius`, `b_site_delta` | Octahedral-site chemistry |
| Cross-site | `a_b_radius_ratio`, `total_entropy`, `phonon_scattering_factor` | Pyrochlore stability, phonon scattering |
| Lattice-derived | `lattice_parameter`, `lattice_volume`, `density_theoretical` | Used for thermal model only |

Key feature definitions:
- **δ (delta)** = `sqrt(Σ xᵢ(1 - rᵢ/r̄)²)` — lattice distortion index
- **S_config** = `-R Σ xᵢ ln(xᵢ)` — configurational entropy (J/mol·K)
- **phonon_scattering_factor** = `S_config × δ_total` — composite phonon scattering proxy
- **r_A/r_B** = A-site to B-site mean ionic radius ratio (governs pyrochlore stability)

## Models

Four regressors are compared in cross-validation for every task; the best is automatically selected:

| Model | Notes |
|---|---|
| **GradientBoosting** | Usually best; balanced bias-variance |
| **RandomForest** | Robust; good uncertainty via tree variance |
| **ExtraTrees** | Faster; slightly higher variance |
| **Ridge** | Linear baseline; useful for interpretability |

> Exact CV/test metrics depend on your environment and current data — run the relevant
> `validate_*.py` script (see [Quick Start](#quick-start)) to get current numbers rather
> than relying on figures baked into documentation, which go stale as data is added.

## Adding New Data

New data always goes in **`data/raw/`**, never hand-edited into `data/processed/`.

1. Drop your CSV into `data/raw/` with columns matching (or mappable to) the canonical
   schema in `src/globals.py::CANONICAL_COLS` (`Sample A`, `Sample B`, `Lattice Parameter
   (Å)`, `Thermal Conductivity (W/m/K)`, etc.).
2. Write a small loader function in `src/data/make_combined_dataset.py` (or a dedicated
   `src/data/load_<source>.py` module, following the pattern of `load_icsd.py` /
   `load_aflow.py` / `load_mp.py`) that reads the raw file and returns a DataFrame in the
   canonical schema.
3. Register the loader in the relevant `build_*_dataset()` function(s) —
   `build_combined_dataset()`, `build_single_phase_dataset()`, and/or
   `build_high_entropy_dataset()` — **remembering that each of these currently has some
   loaders commented out** (see [Data](#data) above); simply adding a loader function
   isn't enough if it's never called.
4. Delete the stale files in `data/processed/` (or just re-run the pipeline — it detects
   missing files and rebuilds automatically):

```python
from src.data.load_data import get_lattice_dataset
X, y, names = get_lattice_dataset()   # rebuilds data/processed/*.csv as needed
```

Force re-train with the `--train` flag on `predict_lattice.py` / `predict_rom_latt.py`
after adding data.
